# C1 Failure Ratchet

The baseline records the ten current test identities and eleven admitted signatures in [C1-RATCHET-5ca8d97-v1](https://linear.app/zeka-saas/issue/ZEK-17#comment-0281b80b-a1a6-42d9-b8f8-02bd8d117a05). H1 remains an open historical obligation. A pass leaves the baseline unchanged.

The baseline also records the required test project for each CI profile, the expected initial base counts, and permitted Linux skips. The earlier CI did not retain complete test identities. CI reconstructs the named inventory by executing the exact base revision in the same profiles and comparing each base identity against the candidate. The first comparison needs the independently approved installation grant described below. After installation the exact recorded base or push-before revision supplies the workflow policy, comparator, parser, runner, schema and baseline. Context and artifact checks also bind the two test trees, repository, event, run and attempt.

A candidate may add tests. All new tests must pass and the previous base identities must still execute. Failed and skipped rows are explicit. The gate checks the native exit against each invocation's test outcomes and checks all project and job evidence. The comparator includes the full sanitized policy diff for validated policy input. A policy change rejected by the initial gate leaves a context rejection receipt before the test or comparison steps. Installed execution rejects any candidate change to the protected policy inputs. A later policy amendment needs a separately approved transition. Adding/replacing signatures or removing obligations requires a separately reviewed change to the trusted policy and tooling with independently accepted evidence.

Existing MVP and Strict Restore remain separate. The Sonar suite profile exercises the same complete solution test command with its collector. The existing Sonar job still owns the analysis and Quality Gate. The focused gateway and owner profiles and Issue 46 project selections are recorded separately. Raw TRX, logs, dumps and attachments remain on the runner. Artifacts contain normalized test rows and hashes tied to the exact run.

## Initial installation

Before the first run, Chief independently verifies the exact candidate commit/tree and canonical execution bundle, and the owner separately approves the exact grant and baseline bytes. A trusted repository administrator may then configure the repository Actions variable `C1_RATCHET_BOOTSTRAP_AUTHORITY` with that approved JSON. Its exact fields are `schema` (1), `repository`, `ref`, `base`, `baseTree`, `source`, `sourceTree`, `bundleSha256`, `resolverSha256` and `baselineSha256`. No default grant is present. The installed baseline remains v1. A separately recorded v2 proposal supplies no authority to this workflow.

The credential-free loader verifies the protected target, Git event/trees, external grant, resolver and complete bundle before it runs the first-use resolver. For a PR, the reviewed source must be exactly the candidate at the current virgin target. An installation push may carry that same reviewed source or its exact two-parent merge from the reviewed virgin base, with the reviewed tree. After the installation push completes, remove the one-time variable through the separately authorized activation procedure.

The loader checks for prior policy history before first use. Once the protected history contains the installation, deletion, renaming or partial replacement fails closed. Installed events use the policy from their exact recorded base/before, with no bootstrap fallback. The verifier checks the selected working policy bytes and applies its baseline schema. A passing check describes the recorded revision. C1 currently does not require a PR to be up to date at merge time. Candidate application and test code still runs as the same runner user, so tracked-policy checks cannot isolate that code from the job or guarantee authenticity against a malicious workflow.

## Required-check activation

1. Have Chief independently verify the source, baseline pin, complete named inventories and the live negative comparator receipt. Keep all existing required checks.
2. Protect the workflow and every other workflow that could emit the same check, the comparator and parser, baseline/schema, test runner, transitive execution policy, and the ownership file. In the current user-owned repository this requires a separately reviewed base-branch CODEOWNERS file, independent code-owner review, stale-approval dismissal and no bypass. An independently controlled required workflow is stronger where repository ownership supports it.
3. Validate equivalent-source direct C1 evidence after the workflow is in C1. Confirm the exact aggregate job appears for both events. Require **C1 Failure Ratchet** from the GitHub Actions provider on the C1 branch only after those checks pass.

Before that protection is enabled, a PR-controlled workflow can replace the workflow or emit the same named check. Independent exact-head review is required for the initial launcher and future gate-code changes. A candidate can remove or replace the workflow, suppress the check or publish the same check name until independent protection is configured. An existing required check tied only to the GitHub Actions app does not prevent that. Keep the required-check activation and any baseline admission separate from this PR.
